# Settings that can't change after the first apply

Several inputs pick a shape once, at create time. Changing one later either
has no effect at all, is rejected by the Kubernetes API, forces the
underlying resource to be replaced (data loss, downtime, or both), or works
but is disruptive enough to plan around rather than discover mid-apply. This
page collects those before the first `terraform apply`, not after.

Each row applies only when the module creates the resource in question: the
CNPG rows need `postgres_backend = "cnpg"`, the Valkey rows `redis_backend =
"valkey"`, and the Ingress rows `create_ingress = true`.

| Setting | Module input | Effect of changing later | What to do instead |
| --- | --- | --- | --- |
| Namespace name | `k8s_namespace` (`create_namespace = true`, the default) | A Kubernetes namespace's `metadata.name` has no rename operation; the `kubernetes` provider replaces `kubernetes_namespace.n8n` outright. Every resource this module creates is scoped to that namespace (the Helm releases, the CNPG `Cluster`, Secrets, the `Ingress`), so replacing it starts from nothing in the new namespace while the old one, and everything in it, is deleted. The Postgres and Valkey PVCs are deleted along with the namespace either way; a `StorageClass` reclaim policy of `Retain` only preserves the underlying `PersistentVolume` (and its backing storage) once the PVC is gone, and that volume then needs manual rebinding before anything can use it again. | Pick `k8s_namespace` before the first apply. To move an existing deployment to a different namespace, treat it as a migration: stand up the new namespace, point a fresh `terraform apply` at it, migrate data (a `pg_dump`/restore for Postgres, nothing durable to carry for Valkey's queue), then tear down the old one. |
| Postgres backend | `postgres_backend` (`"cnpg"` the default, or `"external"`) | `postgres_cnpg.tf`'s `kubectl_manifest.cnpg_cluster` and the chart's database wiring are both `count`-gated on this value. Flipping it from `"cnpg"` to `"external"` or back does not migrate data: the old CNPG `Cluster` is simply no longer managed, and CNPG deletes its PVC when the `Cluster` goes, regardless of the bound `StorageClass`'s reclaim policy; a `Retain` policy preserves only the underlying `PersistentVolume` and its backing storage once the PVC is gone, not the PVC itself, and that volume then needs manual rebinding before anything can reuse it. n8n starts talking to whatever `db_host` now points at, as an empty server from n8n's point of view. | Decide the backend before the first apply. To migrate between them later, `pg_dump` the CNPG database and restore it into the external server (or the reverse), then flip the variable once the target already holds the data. |
| Redis backend | `redis_backend` (`"valkey"` the default, or `"external"`) | Same shape as the Postgres backend: `redis_valkey.tf`'s `helm_release.valkey` is `count`-gated on this value. The `"external"` backend is always caller-owned; this module never manages that backend, only points n8n at whatever `redis_host` says. Flipping from `"valkey"` to `"external"` drops the in-cluster Valkey release and n8n starts against an empty queue; flipping back creates a fresh Valkey release, equally empty. Queued-but-not-yet-executed jobs are lost; already-written execution data in Postgres is unaffected. | Decide the backend before the first apply. The Bull queue is not a system of record, so there is nothing to migrate: flip the variable during a maintenance window and let in-flight executions drain or be re-triggered. |
| CNPG database name and owner | `cnpg_database_name`, `cnpg_database_owner` (`postgres_backend = "cnpg"`) | The module's own variable description is explicit: "changing it on a live deployment does not rename anything, the operator bootstraps the database once, at cluster creation." CNPG's `bootstrap.initdb` only runs when the `Cluster` is first created; Terraform re-applying the manifest with a new name just changes a field CNPG never reads again. n8n keeps connecting to the original database and owner regardless of what the input now says. | Pick both before the first apply. To actually rename or re-own the database later, do it in Postgres directly (`ALTER DATABASE … RENAME TO …`, `ALTER DATABASE … OWNER TO …`) and keep the variables in sync with reality afterward, since the module will not notice the drift either way. |
| CNPG storage size | `cnpg_storage_size` | A PVC's `resources.requests.storage` can only grow, never shrink, and growing it only works at all when the bound `StorageClass` has `allowVolumeExpansion: true`. On a class that does not support it, raising this value is accepted by the `Cluster` spec but the underlying PVC resize request is rejected by the API server. Lowering it is rejected outright. | Size generously before the first apply; a volume provisioner that is slow to reclaim space makes over-provisioning cheap relative to resizing. Confirm `allowVolumeExpansion` on the target `StorageClass` before relying on raising this later, and never lower it. |
| CNPG storage class | `cnpg_storage_class` | `storageClassName` on a Kubernetes PVC is immutable once bound; CNPG's `Cluster` spec does not reformulate the field after the PVC exists, so re-applying with a new class changes nothing on the already-bound volume. | Decide the class before the first apply. Moving to a different class later means a new `Cluster` (or a CNPG-assisted volume migration, outside what this module drives) and a restore. |
| CNPG Postgres major version | `cnpg_postgres_image_tag` | Bumping the PostgreSQL *major* encoded in this tag (e.g. `16` → `18`) is treated by CloudNativePG as a request for an offline in-place upgrade: it stops every pod in the `Cluster`, replicas included, runs `pg_upgrade` in a job, and brings the cluster back on the new major with the database unavailable for the whole of it. It only works between images built on the same OS distribution; crossing distributions (bullseye → trixie, as this module's own default jump does) fails the job outright with nothing upgraded. The module's own CHANGELOG warns of exactly that unsupported crossing for its own default bump; that is a warning against attempting it, not a record of a run that was attempted and failed. A *minor* bump on the same major is comparatively mild: it changes the Cluster spec and triggers CNPG's own rolling restart, no `pg_upgrade` involved. | Pin the tag matching the running major before taking a module version whose default has moved past it (the module's CHANGELOG calls out every such jump). Plan the major upgrade as its own deliberate change, rehearsed somewhere that does not matter, with a backup taken first; if the job fails, reverting the tag to the previous major lets the operator drop the failed job and restart cleanly, no data touched by the failed attempt. |
| Valkey storage size and class | `valkey_storage_size`, `valkey_storage_class` | Same PVC-expansion and immutable-`storageClassName` constraints as the CNPG rows above, applied to the single-node Valkey PVC. | Decide both before the first apply. Because Valkey here is a disposable queue, not a system of record, the practical fallback if a resize or class change is truly needed is to let the release recreate the PVC and accept the dropped queue, rather than migrating it. |
| n8n encryption key | `n8n_encryption_key`, `n8n_encryption_key_secret_ref` | Not enforced by the Kubernetes API, but a one-way door all the same: changing the effective key to a new value against a database that already holds credentials makes every stored credential permanently unreadable, with no recovery path on n8n's side. The module's own variable description calls this out directly: it is the instance's master key, set once, never rotated through this input. | Back up the generated key immediately after the first apply (`terraform output -raw n8n_encryption_key`); see [`docs/post-deployment.md`](./post-deployment.md). Only ever set this input to a non-null value for a brand-new, empty database, or to restore the exact original key into a rebuilt deployment pointed at data already encrypted under it. |
| Binary data mode | `n8n_binary_data_mode` (`"database"` the default, or `"filesystem"`) | Switching modes does not migrate already-stored binaries: data written under `"database"` stays base64 in Postgres rows and is invisible to a pod now reading from the filesystem path, and vice versa. The module's validation only requires a writable `n8n_extra_volume_mounts` entry covering `n8n_binary_data_path`, backed by a declared `n8n_extra_volumes` entry; it cannot verify the backing volume is actually writable at the storage layer or genuinely shared (RWX) across pods. Callers must supply a volume that really is shared and writable across all three pod types, because main, worker and webhook-processor each handle different stages of one execution; validation can pass while the wiring is still wrong, and getting it wrong reports success and silently loses the payload. | Decide the mode before binaries accumulate. To move from one mode to the other on a live deployment, export and re-import the affected executions' binary data through n8n itself; there is no in-place conversion the module performs. |
| Ingress class and TLS secret naming | `k8s_ingress_class_name`, `k8s_ingress_tls_secret_name` | The TLS Secret name depends only on the host (or `k8s_ingress_tls_secret_name` when set); changing `k8s_ingress_class_name` alone leaves it unchanged, so the new `Ingress` points at the same Secret the old one did. What changes is which controller serves the `Ingress`: a different controller may not watch the new class at all, and a cert-manager instance configured for the old controller's conventions may never notice the `Ingress` to renew the certificate in that Secret before it expires. Changing `k8s_ingress_tls_secret_name` itself, or the host, is what actually orphans the previous Secret. | Pick the ingress class and TLS secret naming scheme before the first apply, particularly on a cluster running more than one ingress controller. |
| n8n domain | `n8n_domain` | n8n advertises this as `N8N_HOST` always. `N8N_WEBHOOK_URL` follows it only when both `n8n_webhook_url` and `k8s_ingress_host` are unset; set either one and `N8N_WEBHOOK_URL` follows that value instead, so changing `n8n_domain` alone does not always change the registered webhook URL. Every third-party integration that has stored a webhook callback URL has baked the old value in. The module creates no DNS record either way, so changing the domain also means re-pointing DNS yourself and re-registering every external webhook subscription that used the old hostname. | Treat the primary domain as fixed once any workflow has live external integrations; add further hostnames through `n8n_additional_domains` instead of replacing the canonical one. |

This list covers module-level and Kubernetes-level constraints only. It is
not a substitute for reviewing
[`docs/shared-responsibility.md`](./shared-responsibility.md), which covers
who owns each of the cluster-wide pieces (the ingress controller,
cert-manager, the CNPG operator, KEDA, the default `StorageClass`) these
settings interact with.
